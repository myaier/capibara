# 完成结果与「未读」

「已完成」描述任务结果，「未读／已读」描述用户是否已经查看这个完成结果。观测台分别保留这两个状态：标为已读不会降低完成轮次数，也不会把完成任务改成运行中。

未读状态以 Paseo 宿主报告为准。当前完成结果同时带有 `requiresAttention: true` 和 `attentionReason: "finished"` 时，可以进入「未读」（旧版称「待收菜」）。未归档且已确认完成的结果中，明确的 `requiresAttention: false` 表示宿主已确认阅读；没有报告这个字段时，阅读状态保持未知，不能默认视为已读或未读。归档会话不进入「未读」；归档本身也会清除 attention，因此归档后的 false 单独不能证明已经读过。

仅打开观测台中的详情、时间线、诊断或分析报告不会自动清除未读状态。用户点击「标记已读」或「已读并看下一个」才会提交完成结果的时间戳与用户消息时间戳，宿主确认后同步清除对应的完成提示。审批、问题和执行错误提示不属于这个操作的目标。

进入 Paseo 原生会话后，原生阅读状态会通过目录更新同步到观测台。插件保存的阅读回执包含完成时间与对应用户消息时间，用于宿主清除 attention 字段后保留这次完成结果的身份。新的完成结果产生新时间戳，旧回执不能使它自动变为已读。同步失败时保留未读提示，允许用户重新确认。

开发预览覆盖：两个未读结果、一个已读结果、深层子任务的父级上下文、详情浏览无副作用、显式确认、原生阅读同步、新完成结果再次出现、确认失败及归档隔离。截图和预览数据均为模拟，不会更改真实 Agent。


原生完成提醒时间戳是这次结果的确认标识；生命周期 hook 的接收时间可能晚几毫秒，不会替换这个标识。读取状态与完成状态分开，避免已读后从完成退回空闲。对于插件启用前已清除原生提示、且没有保留终态证据的会话，插件不会从普通 idle 推测完成。

已载入的会话，已读回执只在原生响应和后续复查均确认成功后保存，读取范围限定单个 agent。宿主没有载入的会话（`closed`，daemon 重启后全是这样）例外：清除提醒会让宿主先载入它（Claude Code 等因此常驻一个进程，ACP 会话根本载入不了），所以插件核对提醒令牌和提示词时间后只在本地记回执，不调用清除；Paseo 自己的提醒在下次载入会话时清除。Paseo 的清除接口没有原子版本条件；插件通过精确时间校验、生命周期代数与复查检测并发变化，变化时不宣称确认成功。它不会调用工作区级清除；标记已读也不会批准或拒绝审批请求（就地审批是另外的、每条都要用户点按的操作）。

连续两轮未读时，宿主的提醒时间仍停在第一轮。「标记已读」清的是宿主的提醒，回执记的是页面显示为未读的那一轮的完成时间，由服务端用插件观测到的结束时间核实；所以归档、重启、恢复会话后仍显示已读。

心跳（以及别的系统通知）开新一轮时不带用户消息：会话的最后发言时间不变，提醒也停在第一轮，单看宿主的这两个时间分不出是哪一轮。插件把自己看到的这一轮开始时间记在记录上；它晚于宿主的提醒时间，就说明提醒属于上一轮，这时完成时间、未读、回执、稍后处理和快捷回复都按这一轮算：回执记这一轮的确切结束时间（服务端只认这个时间，上一轮的时间会被判为「完成结果已有更新」），结果按轮次读取和缓存，屏幕上显示的确实是这一轮的结果才能标记已读。待回复（它在问你）的「标记已读」没有完成时间可核对，所以带上页面显示的那一轮（插件看到的开始和结束时间）：服务端核对最新观测到的仍是这一轮，才清提醒或为没载入的会话记回执；页面还停在上一轮的提问时返回「这之后它又跑了一轮」，页面随即重新读取。快捷回复「继续」发出前清提醒，也带上它回答的那一轮的开始时间：服务端核对最新观测到的一轮仍从这个时间开始才清，插件没有这一轮的记录、读不到，或者记录正在报错（例如保存的事件历史损坏后重新开始，还没保存成功）时不清，所以回复因为换了一轮被拒绝、或因为核实不了这一轮而没发时，新一轮的提问仍然计入需要处理；待回复的「标记已读」在记录报错时同样不清，提示稍后再试。插件漏看了某一轮的开始（例如那一刻正在重载）时，这一轮仍按宿主的时间判断，和以前一样。

停下的原因（额度用尽、空轮、可能未收尾）不论这一轮以「已完成」还是「空闲」结束，没看过就计入需要处理；子 Agent 也计入，不能稍后处理。宿主为这一轮发过提醒的，在 Paseo 里打开会话、在观测台点「知道了」，清掉提醒就算看过（「知道了」只清提醒，不记完成回执）。宿主关闭会话时还没结束的那一轮，宿主不发提醒，只有在观测台点「知道了」才算看过，记录保存在插件的观测文件里，重启后仍然有效。
